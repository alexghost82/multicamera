# Architecture-Aware Migration

Проводит исследование существующей функциональности и, только после отдельного явного утверждения, помогает перенести выбранные возможности в другой проект. Переносит поведение и необходимые внутренние механизмы, адаптируя их к целевой архитектуре; не копирует код механически.

## Активация и режимы

- Запускайся только по явному вызову пользователя, например `/architecture-aware-migration ANALYZE ...`. Не инициируй workflow по событиям, расписанию, изменению файлов, открытию проекта или Git-действиям. Не устанавливай hooks, watchers или scheduled tasks.
- Поддерживаемые режимы: `ANALYZE` и `IMPLEMENT`. Если режим не указан, считай его `ANALYZE` и уточни недостающие параметры. Не выдавай условные команды за существующие CLI-команды.
- `ANALYZE` только читает source и target. Разрешено записывать перечисленные ниже документы только в явно согласованный `OUTPUT_DIRECTORY`; не меняй исходный код, конфигурацию, зависимости или инфраструктуру проектов. По завершении остановись и представь план. Не переходи в `IMPLEMENT` без отдельной команды пользователя.
- `IMPLEMENT` доступен только после явного утверждения конкретного плана, его области, функций и разрешённых изменений. Выполняй только утверждённое. Утверждение анализа или плана само по себе не означает разрешение на реализацию.
- Останавливайся и запрашивай решение, если обнаружена опасная несовместимость, нужен неутверждённый файл/зависимость/рефакторинг, проверка требует внешнего воздействия или требования противоречат друг другу.

## Входные параметры

Определи значения из команды и контекста; повторно уже известное не спрашивай. Запроси только недостающее:

- `SOURCE_PROJECT_PATH`: локальный исходный проект.
- `TARGET_PROJECT_PATH`: локальный целевой проект.
- `FEATURES_TO_MIGRATE`: перечень выбранных функций.
- `OUTPUT_DIRECTORY`: каталог для документов и отчётов.
- `MODE`: `ANALYZE` или `IMPLEMENT`.
- Для `IMPLEMENT`: утверждённый план/версия, одобренные функции и точные границы изменений.

Проверь, что проекты доступны для чтения, source и target различимы и не вложены друг в друга: при пересечении их каталогов остановись, так как нельзя гарантировать `SOURCE READ-ONLY`. Output-путь не должен приводить к записи в source. Предпочитай output вне обоих проектов; если он находится внутри source, не записывай туда. Перед созданием документов проверь, существуют ли файлы с такими именами; не перезаписывай их молча, запроси разрешение или предложи новый каталог результатов. Если параметр отсутствует, недоступен или неоднозначен, уточни его до продолжения.

Если `FEATURES_TO_MIGRATE` не задан:

1. Выполни анализ source и сформируй каталог реально обнаруженных возможностей.
2. Отделяй подтверждённые возможности от гипотез и незавершённых частей.
3. Предложи пользователю выбрать функции и дождись ответа.
4. Не включай весь проект в перенос по умолчанию. После выбора продолжи анализ выбранного объёма; не начинай реализацию.

## Границы и безопасность

- Source всегда `READ-ONLY`: никаких правок, форматирования, генерации файлов, установок, конфигурационных изменений или запуска команд, способных изменить его состояние.
- В `ANALYZE` изучай исходники, конфигурацию, документацию и тесты статически. Не запускай приложение, тесты или миграционные скрипты, если их побочные эффекты не доказанно безопасны и отдельно не разрешены.
- Не устанавливай зависимости и не выполняй deployment, изменение инфраструктуры, production, DNS, сетевых правил, секретов, системных служб, политик безопасности или данных без отдельного конкретного разрешения. Не запрашивай и не раскрывай секреты.
- В `IMPLEMENT` до первой правки проверь Git status и текущий commit в target, незакоммиченные изменения, имеющиеся тесты и откат. Если Git недоступен или каталог не Git-репозиторий, явно зафиксируй ограничение; не выдумывай commit и не подменяй откат. Не перезаписывай пользовательские изменения.
- Не выполняй `git reset --hard`, `git clean -fd`, force push, удаление данных и другие разрушительные действия без отдельного явного разрешения на конкретное действие.
- Сохраняй инструкции проекта, включая AI1 safety, deployment, resource и approval gates. При конфликте следуй более строгому ограничению и запроси решение.
- Не утверждай, что функция, устройство, API, сборка или тест проверены, если соответствующую проверку фактически не выполнял. Моки не являются доказательством работы реального оборудования.

## Процедура ANALYZE

### 1. Зафиксируй область

Подтверди режим, пути, выбранные функции и место для документов. Отметь ограничения доступа, известные требования и применимые инструкции проектов. Веди source и target как read-only. Сначала исследуй только нужные архитектурные точки и расширяй чтение по цепочкам вызовов выбранной функциональности.

### 2. Исследуй source и построй функциональный каталог

Определи архитектуру и модули, языки/фреймворки, интерфейсы, функции, сервисы, модели данных, состояние, хранение, API и аппаратные интеграции, конфигурацию, безопасность, зависимости, тесты и правила сборки/развёртывания.

Для функций исследуй фактические точки входа и реализации, не ограничивайся именами файлов и UI. По каждой функции проследи применимую реальную цепочку, например:

`USER ACTION / SYSTEM EVENT -> EVENT HANDLER -> BUSINESS LOGIC -> APPLICATION SERVICE -> BACKGROUND PROCESS / API / HARDWARE -> RESULT PROCESSING -> STATE UPDATE -> USER FEEDBACK`

Если цепочка иная, зафиксируй фактический порядок. Найди связанные классы, методы, интерфейсы, структуры, зависимости, вызовы и условия; побочные эффекты; фоновые задачи и порядок инициализации; данные на входе/выходе; обработку ошибок, повторов, восстановления и освобождение ресурсов.

Отдельно проверь event subscriptions, triggers, scheduling, async/threading, concurrency, singleton/global/shared state, владение ресурсами, сеть, транзакции и cleanup. Отмечай общие сервисы, используемые несколькими функциями. Указывай конкретные пути файлов и символы; привязывай вывод к участкам реализации, доступным в редакторе. Не придумывай отсутствующие детали.

Каждое существенное утверждение маркируй одним из статусов:

- `CONFIRMED`: подтверждено кодом, конфигурацией или реально выполненной проверкой; укажи доказательство.
- `INFERRED`: вывод из имеющихся свидетельств, но прямо не подтверждён; опиши основание и неопределённость.
- `UNKNOWN`: данных недостаточно; укажи, что нужно проверить.
- `NOT IMPLEMENTED`: необходимая функция явно отсутствует или имеет заглушку; приведи доказательство.

Создай в `OUTPUT_DIRECTORY` документ `SOURCE_FUNCTIONAL_INVENTORY.md`, на русском языке. Сгруппируй функции по модулям, укажи общие сервисы отдельно. Для каждой функции заполни:

- `FUNCTION ID`, `FUNCTION NAME`, описание;
- `SOURCE FILES`, точки входа, классы/функции/методы;
- зависимости, execution flow, условия запуска;
- фоновые операции, data flow, внешние интеграции;
- side effects, error handling/recovery, implementation status;
- migration complexity и обоснование.

### 3. Если функции не выбраны, остановись на выборе

Представь каталог обнаруженных возможностей и попроси выбрать функции. Не составляй область переноса за пользователя. После его выбора продолжи шаги 4–6 для выбранных функций.

### 4. Исследуй target

Определи архитектуру, технологии, модули и соглашения, уже существующие функции и сервисы, API, модели, state management, зависимости, конфигурацию, безопасность, сборку, тестирование и deployment. Найди функциональные дубликаты и точки безопасного повторного использования. Сохраняй целевую архитектуру; не заменяй имеющиеся механизмы без доказанной необходимости.

### 5. Построй карты зависимостей и совместимости

Создай `DEPENDENCY_MAP.md` для выбранных функций. Включи прямые и транзитивные зависимости, общие и платформенные/аппаратные компоненты, библиотеки, разрешения, конфигурацию, фоновые службы, порядок инициализации и жизненный цикл. Отрази скрытые зависимости: singleton/global/shared state, конкурентный доступ, подписки, владение ресурсами, сетевые соединения, транзакции и cleanup. Разделяй необходимые зависимости и необязательные; рекомендуй минимально необходимую интеграцию.

Создай `COMPATIBILITY_REPORT.md`. Сравни source и target по языкам/фреймворкам и версиям, моделям данных, архитектурным паттернам, lifecycle/state, concurrency, безопасности, памяти/CPU/GPU, устройствам, портам, конфигурации и deployment. Для каждого конфликта укажи `PROBLEM`, `CAUSE`, `IMPACT`, `RISK`, `RECOMMENDED SOLUTION`, `ALTERNATIVE SOLUTION` и статус доказательств. Предлагай адаптацию вместо механического переноса. Если безопасная адаптация не определена, остановись и запроси решение.

### 6. Подготовь план и чеклист, затем остановись

Создай `FUNCTIONAL_MIGRATION_PLAN.md` со следующими разделами:

1. Executive Summary
2. Source Project Overview
3. Target Project Overview
4. Functional Inventory
5. Selected Features
6. Source Execution Flows
7. Dependency Mapping
8. Compatibility Assessment
9. Proposed Target Architecture
10. Integration Points
11. Required Adaptations
12. Files to Create
13. Files to Modify
14. Dependencies
15. Configuration Changes
16. Security Assessment
17. Resource Assessment
18. Migration Stages
19. Testing Strategy
20. Regression Testing
21. Rollback Strategy
22. Risks
23. Acceptance Criteria
24. Approval Requirements

Для каждого этапа задай действия, конкретные целевые файлы, зависимости, изменения, риски, проверки, критерии завершения и процедуру отката. Отделяй факты от предположений; явно указывай неизвестное и непроверенное. Используй Adapter, Facade, Dependency Injection, Service Layer или Event-Driven Integration только при реальной необходимости.

Создай `MIGRATION_CHECKLIST.md`. Для каждой выбранной функции добавь незакрытые пункты:

- `[ ]` Source implementation analyzed
- `[ ]` Execution flow documented
- `[ ]` Dependencies identified
- `[ ]` Target architecture analyzed
- `[ ]` Compatibility verified
- `[ ]` Integration design prepared
- `[ ]` Risks documented
- `[ ]` Migration approved
- `[ ]` Implementation completed
- `[ ]` Build successful
- `[ ]` Tests passed
- `[ ]` Integration verified
- `[ ]` Regression tests passed
- `[ ]` Acceptance criteria satisfied

Отмечай пункт выполненным только при наличии доказательства. Перечисли проверки, которые не проводились, и причины. После записи документов покажи краткое резюме, риски и вопросы для утверждения; затем `STOP`. Не запускай реализацию.

## Процедура IMPLEMENT

### 1. Проверь утверждение и границы

Убедись, что пользователь явно указал утверждённый `FUNCTIONAL_MIGRATION_PLAN.md` (или его конкретную версию), выбранные функции и разрешённые изменения. Сверь изменения с планом. Если утверждение неясное, устаревшее или не покрывает нужную правку, остановись и запроси уточнение. Не расширяй scope самостоятельно.

### 2. Подготовь target и безопасный откат

До изменений зафиксируй Git status и commit, незакоммиченные изменения, текущие тесты и способ отката; границы правок должны соответствовать утверждённому плану. Не включай source в команды записи. Если нет надёжного отката для рискованного шага, запроси решение до выполнения.

### 3. Реализуй небольшими этапами

Вноси минимальные изолированные изменения в target, следуя его стилю и архитектуре. Переиспользуй существующие API и сервисы, не создавай дубликаты, не добавляй ненужный рефакторинг и зависимости. Удерживай изменения внутри разрешённых файлов. Если нужны неутверждённые файлы, конфигурация, права, инфраструктура или новая архитектура, остановись и запроси новое утверждение до изменения.

После каждого этапа:

1. Проверь diff и соответствие утверждённой области.
2. Выполни согласованные компиляцию/сборку и подходящие тесты; сначала проверь их возможные побочные эффекты.
3. Проверь интеграцию и регрессии в пределах доступной среды.
4. Если обязательная проверка не прошла, остановись. Не скрывай ошибку, не имитируй успех и не продолжай следующие этапы до разбора и разрешения.
5. Обнови отчёт и checklist фактическими результатами.

Не заявляй о полноценной end-to-end проверке, если не прошёл весь путь: действие/событие, handler, логика, сервисы, реальный API/оборудование, результат, состояние, UI feedback, ошибки и cleanup. Отмечай отдельно `UNIT TESTED`, `INTEGRATION TESTED`, `END-TO-END TESTED`, `NOT VERIFIED`. Если оборудование или внешняя система недоступны, укажи это ограничение.

### 4. Отчитайся

Создай в согласованном `OUTPUT_DIRECTORY`:

- `MIGRATION_EXECUTION_REPORT.md`: выполненные изменения, затронутые файлы, зависимости и конфигурация, отклонения от плана, проблемы и статус каждой функции.
- `VALIDATION_REPORT.md`: команды и реальные результаты сборки/тестов/интеграции/regression/E2E, непроведённые проверки, ограничения и оставшиеся риски.

Пиши отчёты по-русски, сохраняя технические имена без перевода. Не отмечай непроведённые проверки успешными. После завершения утверждённого объёма сообщи результаты и границы проверки; не выполняй deployment или неутверждённую следующую работу.

## Общие критерии качества

- Сохраняй существующее поведение target и придерживайся его архитектуры.
- Переноси только выбранные функции и необходимые им зависимости.
- Для выводов указывай доказательства и различай факт, предположение и неизвестное.
- Не заявляй полную совместимость без достаточных свидетельств.
- Не удаляй и не затирай пользовательские изменения.
- Не подменяй реальную проверку mock-данными или фиктивными результатами.
- Документируй риски, решения, ограничения и способ отката.
- При сомнении выбирай остановку и запрос явного решения, а не неутверждённое действие.
