## Реализованные изменения первого этапа

### Инциденты и аудит — A-01

Мутация и атомарная запись JSON выполняются под одной блокировкой каждого хранилища. Устаревший снимок больше не может перезаписать новую мутацию в рамках одного экземпляра хранилища. Ошибки чтения/записи доступны через `lastPersistenceError` и выводятся в уведомлении приложения. После ошибки чтения исходный файл не перезаписывается пустым массивом; новые события остаются в оперативной памяти. После временной ошибки записи следующая мутация повторяет сохранение всего состояния.

Это не межпроцессная синхронизация. Одновременная работа двух экземпляров приложения с одним каталогом данных не является проверенным режимом. Нет гарантии сохранения новых событий при отказавшем диске и последующем аварийном завершении процесса; ошибка теперь наблюдаема. Для запуска после повреждения истории требуется восстановление файла оператором.

Проверки: 100 конкурентных добавлений с изменением статуса и повторной загрузкой; сохранность журнала; повреждённый JSON; отказ записи и последующая повторная запись.

### Lifecycle — A-02, A-04

Результаты inference и вторичной проверки связаны с поколением сессии и камеры. Проверки происходят перед работой, перед изменением FSM/завершением задания планировщика и перед публикацией на MainActor. Stop, смена настроек, замена camera session и изменение reconnect counter инвалидируют старую работу. Остановка камер вызывает остановку движка. Нельзя объявить найденный на диске Pose-пакет готовой runtime-сессией; отсутствие Pose больше не описывается как работающая object-level аналитика.

Отменяются загрузка модели и вторичные проверки. Нативный синхронный Core ML вызов не прерывается посередине; его устаревший результат отбрасывается. Исторические запросы и консультации отменяются при shutdown приложения.

### Вторичная проверка — A-03

Свободный текст не определяет подтверждение. Контракт: JSON с `decision` (`confirmed`, `rejected`, `inconclusive`) и непустым ограниченным `summary`, без дополнительных полей. Невалидный ответ/ошибка транспорта дают `unavailable`. Отрицательное заключение не закрывает первичное событие падения. Незавершённые вторичные проверки при следующем запуске получают `unavailable` с объяснением прерывания.

### Память и агент — M-01–M-04, частично M-07

Перед первой модельной репликой выполняется ограниченный поиск по timeline, кадрам памяти, трекам и атрибутам. Модель получает каталог источников. Ссылки в ответе сверяются с идентификаторами фактически полученных структурированных записей; модельные ссылки на неизвестные записи отбрасываются. Ответ без проверяемых ссылок не выдаётся как подтверждённый исторический вывод. В истории доступен сворачиваемый список источников с record ID, камерой и временем, когда эти поля имеются.

Сохранение итоговой реплики и `last_response_id`/задолженности function outputs выполняется одной транзакцией SQLite. Ошибки критического chat-пути обрабатываются явно. SQLite диагностирует ошибки в `lastPersistenceError`, в том числе для фоновых callers, использующих `try?`. Чтение памяти использует переданное время запроса, а не `max(now, Date())`, которое разрушало исторические тестовые данные через retention.

Результаты инструментов и OCR рассматриваются как недоверенные данные. Их строки не разбираются как дополнительные записи provenance. Это защита границы и правил доступа, а не доказательство полной устойчивости LLM к prompt injection. Проверка существования ссылки не доказывает семантическую правильность каждого утверждения.

### Передача данных и действия — S-02, S-03

Внешнее согласие повторно проверяется непосредственно перед HTTP transport. Для облачного Responses backend, включая loopback backup relay, дополнительно требуется текущий облачный режим. Переход на локальный режим блокирует отложенную облачную отправку. Cross-origin HTTP redirects запрещены, чтобы loopback-сервис не мог перенаправить тело запроса на другой host/port/scheme.

Подтверждение оператором проверяется до эффектов. Поддерживаемые типы и параметры действия ограничены. Решение и изменения SQLite выполняются в одной транзакции; состояние identity resolver обновляется после commit. Повторное выполнение и подтверждение ранее отклонённого предложения не разрешены. Proposal сравнивается внутри блокировки с тем, который прошёл валидацию. SQL-инструмент ограничен readonly statement, числом строк и бюджетом исполнения 0,5 с.

`merge_identities`/`split_identity` сохраняют имеющуюся модель операций с gallery profiles. Полная семантика переноса атрибутов, посещений и всех производных индексов требует отдельной приёмки; не считать эти операции доказанно полными по всему графу памяти.

### Совместимость — A-05

`CameraWall.GhostCredentials`, `GhostKey` и `ghost_*` сохраняются как идентификаторы существующих хранилищ. Их косметическое переименование без отдельной проверенной миграции не выполняется. Новые поля structured answer опциональны при чтении старых сообщений.

### Уточнение нагрузки от пользователя

Подтверждён одновременный Pose-анализ всех 64 камер. Отображение остаётся 1080p25. Пользователь подтвердил Pose-анализ каждого кадра: 25 FPS на каждую из 64 камер, суммарно 1600 inference/s, без аналитического sampling/drop. Этот показатель нельзя подменять FPS декодирования или средней частотой по части камер. Локальная машина: Apple M5, 24 GiB RAM, 10 CPU cores. Проверенный sustained 64-camera benchmark отсутствует. ### Обязательный capacity gate: 64 × 25 Pose

- Текущий scheduler не соответствует этому режиму: настройки ограничивают sampling 15 FPS, по умолчанию 4 FPS / idle 1,5 FPS, один ожидающий кадр на камеру заменяется более новым с увеличением droppedFrames. Синхронные вызовы Pose в локальном движке выполняются на последовательной очереди.
- Простое увеличение настройки FPS не обеспечивает анализ каждого кадра. Неограниченная очередь запрещена как решение перегрузки: она скрывает дефицит производительности ростом RAM и задержки.
- Минимальная требуемая устойчивая пропускная способность — 1600 обработанных кадров/с. Это эквивалентно 0,625 мс на кадр суммарной пропускной способности, а не ограничению latency одного параллельного inference.
- Ранее записанные Python/Core ML smoke-измерения около 10 мс на кадр не являются новым Swift benchmark. Они указывают на существенный риск нехватки мощности у последовательного пути, но не дают доказанного коэффициента масштабирования или числа необходимых устройств.
- Перед изменением execution architecture измерить Swift/Core ML throughput с текущим артефактом, затем с декодированием 1080p25 и обработкой результатов. После этого проверить варианты параллельных экземпляров/batching только при поддержке модели и доказанном улучшении, учитывая суммарную память и конкуренцию с Qwen/ReID.
- Приёмка требует счётчиков по каждой камере: received/decoded/submitted/completed/dropped, исходный frame ID, длительность/период измерения, отсутствие растущего backlog и p50/p95 latency. Сбой или нехватка мощности должны явно отражаться как невыполнение режима.
- Sustained 64-camera test и допустимая end-to-end latency пока не согласованы и не выполнены. Архитектура выполнения требования на одном Apple M5 не объявляется готовой; масштабирование на другие узлы потребует отдельного решения и не должно вводить обязательный ручной worker workflow.

## Второй этап: локализация, доказательства и GUI инцидентов

### Актуальное ограничение scope

По последующему указанию пользователя нагрузка **64 камер с одновременным Pose-анализом временно исключена из проверок**. Ранее согласованное требование 25 Pose FPS на каждую из 64 камер сохраняется как будущая цель. Нагрузочные сценарии с 64 реальными или синтетическими потоками в этом проходе не запускались. Небольшой существующий unit test алгоритма планировщика не является таким нагрузочным испытанием.

### Реализовано

- Добавлены переводы настроек/ошибок Pose, интерфейса глав памяти и worker-диагностики. Source audit больше не принимает литералы сравнения идентификаторов (`default`, `user`) и reverse-DNS service names за UI-подписи. Реальные подписи ternary-ветвей продолжают проверяться. Англоязычная hardcoded запись об успешном перестроении знаний заменена локализуемым ключом.
- Проверены 460 ключей, извлечённых Swift-компилятором, и исходные UI-строки. Найденные compiler-only ключи `--` и `Δ %@` явно учтены. Добавлены переводы известных шаблонов пояснений детектора; числа, имена зон оператора и неизвестные внешние сообщения не изменяются. Это не автоматический перевод AI-ответов или пользовательских данных.
- Дедупликация/подавление выполняется до создания evidence. Пакет использует канонический incident ID; повторные события не создают дополнительные пакеты и не перезаписывают существующие доказательства.
- Новый пакет сначала полностью записывается в скрытый staging-каталог и публикуется rename. Повреждённый существующий manifest не перезаписывается. Ошибки создания, post-event записи и удаления доступны в диагностике.
- Счётчик post-event кадров меняется только после успешной записи. Суммарный размер JPEG пересчитывается, чтобы повторная попытка не удваивала учёт байтов. Неуспешное удаление по квоте не уменьшает фиктивно учтённый размер.
- При удалении учитывается фактический clip ID, включая старые пакеты с ID, отличным от ID инцидента. Ссылки в инциденте очищаются после удаления. Уведомление об ошибке остаётся доступным при отказе.
- Повторная загрузка Pose инвалидирует старую сессию и сбрасывает именно модель, сохраняя тёплый runtime при обычном Disconnect. Повторные кандидаты не перезапускают уже выполняющуюся вторичную проверку. Кадр для VLM можно подготовить без включения записи evidence на диск.
- Срок подавления сохраняется в JSON и восстанавливается после запуска. Явное повторное открытие инцидента снимает соответствующее подавление. Новое поле опционально при чтении прежних записей.
- В «События» добавлен отдельный центр инцидентов: поиск, камера, фильтр открытых записей, статусы, примечания оператора, вторичная проверка, просмотр кадров, подтверждение/закрытие/ложная тревога/подавление/повторное открытие. Удаление evidence требует подтверждения. Сохранение примечания не меняет статус и имеет отдельную запись аудита.
- Исправлен fallback имени камеры для заданий, взятых из очереди другой камеры: сохраняется известное имя, а не технический UUID-префикс.

### Оставшиеся ограничения

Скрытые staging-каталоги от принудительного прекращения создания evidence, межпроцессная запись в один JSON и атомарность общей операции «удаление файлов + обновление JSON» ещё требуют отдельной recovery/retention стратегии. Отказ файловой системы может оставить неполный набор файлов; приложение не объявляет такую операцию гарантированно атомарной между хранилищами. Перезапуск post-event захвата после аварии не реализован; уже сохранённые кадры и manifest читаются.

Полные GUI-настройки детекторов/зон, проверка реальных RTSP/USB-падений с размеченным видео, глубина retrieval на длинной истории, полный security audit и выпуск остаются отдельными задачами. Production readiness не подтверждена.
